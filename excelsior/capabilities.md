# Capabilities: reusable behavior a class includes

Status: decided (2026-07), not yet implemented. The mixin/trait follow-on from the backlog (backlog.md), the
surface for the mechanism meta.md and shared-params.md fixed. Tier: **including**
a capability is World (a content creator writes `include Openable`), **declaring**
a declarative capability is Mechanics, and a **computed** capability is Meta (a
class-body macro, meta.md). This refines tiers.md, which placed the whole system
at tier 3. Builds on verbs.md (the verb boundary), visibility.md (per-member
visibility), and meta.md (the class-body-macro mechanism).

The mechanism is settled: a capability is a **class-body macro** that expands
into an including class, adding self-fields plus sendable verbs, **safe by
construction** because its member code is self-access in the including class and
it cannot emit the cross-object writes the base layer rejects (meta.md,
shared-params.md). So a capability gives **reuse, not new power**. What was left
open, and what this pass settles, is the surface: the word, the `include`
spelling, how members merge, the collision rules, the required-member contract,
and the boundary that a capability is reuse and not a type. (The earlier notes
call this a "mixin"; the concept is the same, and this pass fixes the readable
name, with the older mentions migrating as touched.)

## The word: `capability`

The construct is spelled **`capability`**. The choice is deliberate, because the
usual names are jargon a new reader must learn before they can read code, which
the readable-surface goal (words a layperson can say and look up) rules out:

- **`mixin`** is a coined term, not an English word at all.
- **`trait`** is an English word, but in programming it primarily names a
  *type* (Rust, Scala, a polymorphic bound), which is a different axis here, so
  it both misleads a programmer and reads as jargon to everyone else.
- **`role`** was the strongest runner-up: Raku chose "role" over the academic
  "trait" for exactly this readability reason. But in a game a "role" reads as a
  part a character plays (a merchant, a healer), which collides with the content
  domain.

**`capability`** is plain English for what the construct actually gives, what an
object can do: a chest gains the **openable** capability, the **lockable**
capability, the **container** capability. It names the affordance, matching how
the audience's own tools frame these (Inform 7 and TADS make openable/lockable
properties of a thing, and game engines compose object affordances), and it has
no competing meaning as a programming term. The type axis keeps its own word,
an **`interface`** (verbs.md decision 5), so the two never collide, and `include`
(also plain English) is the opt-in verb.

## Declaring a capability

A capability is a named bundle of members, declared like a class fragment:

    capability Openable
        requires name is str            // the includer must provide these
        field open is bool = false

        verb open()
            self.open = true
            tell(self.owner, "The ${self.name} opens.")
        endverb

        verb close()
            self.open = false
        endverb
    endcapability

It may declare **fields** (self-state), **verbs** (public, sendable behavior),
**funcs** (private helpers), and **`requires`** clauses (below). This declarative
form is a **class fragment** a Mechanics author writes with no macro code; it is
the gentle face of meta.md's class-body macro. A **computed** capability, one
whose members are generated by compile-time code (a serializer capability that
iterates a record's fields, record-introspection.md), is the procedural macro,
the Meta escape. Both expand the same way; the declarative one is the common
case.

This refines meta.md and tiers.md, which placed capabilities wholly at tier 3:
only the *computed* form needs the Meta layer. Declaring a plain behavior bundle
and including it are Mechanics and World, because reusable behavior across object
classes (openable, lockable, container, readable) is bread-and-butter content
work, not framework-authoring.

## Including a capability

A class opts in with an **`include`** directive in its body:

    class Chest is Container
        include Openable
        include Lockable
        private
            capacity is int = 20
    endclass

`include Name` splices the capability's members into the class **as class-level
members**, at the point of the directive (conventionally the top). A class may
include several capabilities, and a capability may itself `include` another
(transitive expansion, the collision rules below applying throughout). Inclusion
is a separate axis from inheritance: `is Container` names the superclass (the
vertical hierarchy), `include Openable` takes on a horizontal behavior bundle.
The two never share a keyword, so a reader is never in doubt which is which.

The spliced members keep their kinds and visibility (visibility.md): a field is
a private self-field, a verb is a public sendable verb, a func is a private
helper. Every one is self-access in the including class, which is the
safety-by-construction meta.md relies on: the capability's `self.name` is the
including class's field, and the only cross-object reach is a **send to one of
the verbs the class chose to include**, offered with consent at definition time
(shared-params.md).

## Merge and collisions: more-specific wins, peers error

When names collide, one rule covers it: **the more specific member wins, and
peers are a compile error.** Specificity is class-own, then a capability, then
the superclass:

- **A class's own member overrides a same-named capability member.** The class
  is authoritative over what it includes, so declaring `verb open()` in the class
  replaces `Openable`'s `open`. This is how a class customizes a default.
- **A capability member overrides a same-named superclass member.** A spliced
  member is class-level, so it wins over an inherited one, exactly as a class-own
  member would (the existing override path, CLAUDE.md).
- **Two included capabilities declaring the same name is a compile error**,
  naming both sources, because they are peers with no ordering between them. The
  class resolves it by dropping one, or by declaring its own member of that name
  (which wins over both by the first rule).

This is a one-level rule, not a C3 linearization: a reader orders three sources
(own, capabilities, super) and knows peers clash. It keeps the beginner-facing
model simple where PHP's `insteadof`/`as` and Python's MRO are famously not.

## The `requires` contract

A capability usually needs the including class to provide something, a field it
reads or a verb it calls. It states that with **`requires`**:

    capability Lockable
        requires open is bool           // provided by Openable
        field locked is bool = true
        verb unlock(key is obj) ...
    endcapability

`requires MEMBER` lists the fields and verbs the includer must supply, and the
checker verifies them **at the include site**, so a missing one is a clear error
there (`class Chest includes Lockable but provides no field open is bool`) rather
than a confusing error inside the expanded body. Without a `requires` line the
expand-then-typecheck model (meta.md) still catches a missing member, just with a
worse, post-expansion message; `requires` is the contract-and-good-error layer,
and it documents what a capability expects. A `requires` may be satisfied by a
class-own member, an inherited one, or another included capability.

## A capability is reuse, not a type

A capability adds behavior to a class; it is **not** a type you can be
polymorphic over. There is no `param is Openable` accepting any class that
includes `Openable`, and no `x is Openable` test. That role, a named verb-set
with explicit conformance used as a parameter type, is the **interface** work
deferred in verbs.md (decision 5), a distinct axis this pass does not open.
Keeping capabilities to inclusion-only is what preserves shared-params.md's
"reuse, not new powers": a capability rearranges members into a class, it does
not mint a new cross-class abstraction or a new dispatch target. When interface
types land they are the polymorphism axis; capabilities stay the reuse axis, and
a capability's verb set is a natural thing to later expose as an interface, but
that is a separate decision.

## Survey

- **Rust, Scala, PHP traits**: the academic "trait", a named bundle of behavior
  a type takes on. Excelsior takes the reuse half now and leaves the *type* half
  (a trait as a polymorphic bound) to interfaces, and resolves conflicts by the
  simpler more-specific-wins/peers-error rule rather than PHP's per-method
  `insteadof`/`as` operators.
- **Raku roles**: chose the name "role" over the academic "trait" for
  readability ("it better indicates their use case"), the same motivation as
  this pass, which went one word further to `capability` to avoid the RPG-role
  reading in a game.
- **Inform 7 / TADS**: the audience's own tools, where openable and lockable are
  either/or properties of a thing (Inform) or Openable/Lockable classes (TADS);
  the framing of these as capabilities an object has is theirs.
- **Ruby `include Module`, Dart mixins (`with`)**: the `include` opt-in verb and
  the class-then-included-then-super resolution order this pass adopts.
- **ECS components / aspects**: game-engine composition of behavior onto
  entities, the domain motivation; "component" and "aspect" were passed over for
  their engine and aspect-oriented baggage.

Excelsior's stance: a plainly-named `capability` a class `include`s (Ruby's
verb), merged as class-level members with a simple more-specific-wins order, a
`requires` contract for clear errors, safe-by-construction as self-access-only
reuse, and the type/interface role kept separate and deferred.

## Decisions (confirmed)

The seven decisions are confirmed, with `capability` the word (D1). The
implementation (the declarative-capability reader, the `include` class-body
expansion into class-level members, the more-specific-wins/peers-error merge, the
`requires` check at the include site, and the computed capability as a class-body
macro over meta.md) follows; the interface/type role stays the deferred
verbs.md D5 work.

**D1. The construct is spelled `capability`.** "mixin" is coined jargon, "trait"
programming-jargon that primarily means a *type*, and "role" (Raku's readable
pick over trait) collides with the RPG-role reading in a game; "capability" is
plain English for what an object can do (openable, lockable), matching Inform 7 /
TADS / game framing, with no competing programmer meaning. The type axis is the
separate word `interface` (verbs.md decision 5).

**D2. A capability is declared `capability Name ... endcapability`, a bundle of
fields, verbs, funcs, and `requires` clauses.** The declarative form is a
Mechanics-tier class fragment (no macro code); a computed capability whose
members are generated is the Meta-tier procedural class-body macro (meta.md).
Both expand the same way.

**D3. A class includes a capability with the body directive `include Name`**,
which splices its members in as class-level members (fields private self-fields,
verbs public sendable, funcs private), all self-access. Inclusion is a separate
axis from `is` inheritance; a capability may include another (transitive).

**D4. Collisions follow one rule: more-specific wins, peers error.** Class-own
overrides a capability, a capability overrides the superclass, and two
capabilities with the same name is a compile error naming both (the class
resolves by dropping one or declaring its own). A one-level order, not a C3
linearization.

**D5. `requires` states the members the includer must provide**, checked at the
include site for a clear error, satisfiable by a class-own, inherited, or other
included member. Without it, expand-then-typecheck still catches a missing
member, less clearly; `requires` is the contract and good-error layer.

**D6. A capability is reuse, not a type.** No `param is Capability` and no `x is
Capability` test; the parameter-type/polymorphism role is the deferred interface
work (verbs.md decision 5). This preserves "reuse, not new powers": a
capability's only cross-object reach is a send to a verb the class chose to
include.

**D7. Tier: including is World, declaring a declarative capability is Mechanics,
a computed capability is Meta.** This refines tiers.md and meta.md, which placed
the whole system at tier 3; only the computed macro needs Meta, because reusable
behavior bundles are common content work.
