# LP64 for the 64-bit targets

The x86-64 and arm64 targets are genuine **LP64** (64-bit `long` and 64-bit
pointers), so a program's layout and pointer width match the platform psABI and
the Linux glibc/musl headers. The genuine 32-bit targets (ColdFire, RISC-V RV32,
MIPS) are **ILP32** (4-byte `long` and pointers). This note records how the
migration was done; it is complete (see the status at the end).

## Why it was large

The 64-bit backends were first built **ILP32-style on purpose**: the shared IR
treated a pointer as a 32-bit value, addresses were kept in the narrow register
view (`w` on arm64, `e` on x86-64), and the runtime used a low-memory stack and
heap so every address fit in 32 bits. Real LP64 undid that: an address is now a
64-bit value and address arithmetic is 64-bit. The runtime, though, was *not*
moved to full memory: the low-memory stack and heap survive as a bring-up
convenience (the 64-bit address values are correct either way), so that part of
the original ILP32-style design is deliberately kept.

The 64-bit backends already had most of the machinery: a native single-register
`IR_I64`, and load/store that already use the full 64-bit register as the memory
base (the `ra` helper on arm64). So the bulk of the work was in the cc front end
(compute addresses as `i64`) and a per-backend flip, not new instruction
selection.

## Data model

|            | ILP32 (cf, rv32, mips) | LP64 (x86-64, arm64) |
|------------|------------------|----------------------|
| `int`      | 4                | 4                    |
| `long`     | 4                | 8                    |
| `long long`| 8                | 8                    |
| pointer    | 4                | 8                    |
| `size_t`   | (unsigned) 4     | (unsigned) 8         |

Selected at compile time per tool, mirroring the existing backend selection:
a `CC_LP64` define drives `CC_PTR_SIZE` / `CC_LONG_SIZE` (4 or 8). Only the
x86-64 and arm64 cc tools define it.

## Phases (each kept the whole suite green)

All five phases landed; the ✓ phases below were the flip, the first two were the
gated-off seam they turned on.

1. **Data-model seam.** ✓ Introduced `CC_LP64` and
   `CC_PTR_SIZE`/`CC_LONG_SIZE`, threaded through `cc_type_size` /
   `cc_type_align`, `type_to_ir`, and `is_i64_type`. With `CC_LP64` undefined
   the values stay 4 and behavior is byte-identical. This is the seam every
   later phase turns on.

2. **Address roots + core address lowering.** ✓ New `IR_LEA64` / `IR_ADL64`
   opcodes (a symbol / local-slot address as a full 64-bit value), implemented
   on the x86-64 and arm64 backends. In cc, an address-model layer
   (`emit_addr_sym`/`_slot`/`_add`/`_const`/`_scale`, `widen_to_addr`,
   `val_is_wide`) makes the address roots, array/struct decay, index scaling,
   member offsets, and pointer-value load/store pointer-width. Under ILP32
   every helper reduces to the original 32-bit op, so the lowering is
   byte-identical.

3. **Storage classification + flip x86-64.** ✓ `is_i64_type` now covers a
   pointer / function type under LP64, so the width-of-storage sites (args,
   returns, local stores, param slots, and the int↔pointer casts) treat a
   pointer as 8 bytes automatically; pointer arithmetic stays separate through
   the address helpers. A pointer global is an 8-byte `IR_I64` with a `dq`
   relocation. `CC_LP64` is defined for the x86-64 cc tool. The low-memory
   `start_x86_64.asm` runtime is unchanged (addresses stay sub-4GB, so the
   64-bit values are correct). Two size-assertion tests were rewritten to
   check data-model-invariant relations so the one suite passes under both
   models; `cc_t064` locks in the pointer behavior. Green across all four cc
   targets (64 tests each) and the x86-64 i64/ops/fpu tests.

   *(Resolved in phase 5:* at this point an integer literal with an `l`/`ll`
   suffix, or one too large for `int`, was still typed `int`, so a 64-bit
   constant like `1099511627776L` truncated; phase 5 made the lexer record the
   suffix/magnitude and the parser type the literal `long`/`long long`.)

4. **Flip arm64.** ✓ `CC_LP64` defined for the arm64 cc tool. The arm64
   backend already used the `x` view for addresses and had `IR_LEA64` /
   `IR_ADL64` from phase 2, so only the pointer relocation needed widening
   (`.quad sym` for an 8-byte element). `start_arm64.S` is unchanged
   (sub-4GB addresses). Green: `check-cc-arm64` (64/64), the arm64 i64/ops/fpu
   tests, and full check-all with both 64-bit targets on LP64.

5. **64-bit `long` literals and `size_t`.** ✓ The lexer records an `l`/`ll`
   suffix (and a magnitude too big for `int`), and the parser types the literal
   `long` / `long long` (a `cc_type_long` singleton was added), so a 64-bit
   constant no longer truncates. `size_t` / `ptrdiff_t` need no built-ins: a
   header (or user) `typedef unsigned long size_t;` is already the right width
   because `long` / `unsigned long` are data-model-sized, verified on both
   models by `cc_t065`. A compiler-predefined `__SIZE_TYPE__` macro (so system
   headers typedef cleanly without conflicts) belongs with the broader
   use-system-headers work, not here.

The 64-bit targets are LP64.  Remaining ABI gaps (register calling convention,
struct-by-value, `long double`, bitfields) are tracked in the PLAN.md ABI note,
independent of the ILP32-vs-LP64 axis this note closed.

This note covers the **cc** front end, which led the migration. LP64 then
became the model for the whole toolkit on x86-64 and arm64: Kobold (`kpcom`,
0.20.0), and then the in-process C JIT and the stack-ABI tinc / TinScheme
backends. The ILP32-on-64 trick is retired everywhere; only the genuine 32-bit
ISAs (ColdFire, RISC-V RV32, MIPS) are ILP32. The pointer-width axis is unified
in `ir/target.h` (`SKJ_LP64`), derived from the ISA selector (`X86_BITS==64`,
`CC_ARM64`) with no separate per-front-end width macro.

## Status

- Done: LP64 fully replaces ILP32 on x86-64/arm64 for every front end; the
  ILP32-on-64 path is gone, not a kept build variant. The low-memory runtime
  stack survives only as a bring-up convenience for the tinc/scheme AOT tools,
  not an address-width requirement.
- Residual detail (not blocking): the pointer-subtraction result type and the
  `long`-vs-`long long` printf width lowering are a `ptrdiff_t`/`%ld`-vs-`%lld`
  matter that rides on the broader use-system-headers work, not the ILP32-vs-LP64
  axis this note closed.
